# RideShare M5 (Payments) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Take real (Stripe test-mode) payments: hold the passenger's card when they request a seat, charge it when the driver accepts, release or refund it on reject, expiry and cancellation, and show drivers a demo earnings ledger.

**Architecture:** The M1 `payments` module keeps its four functions but gains a provider: `stripe` (Stripe SDK, manual-capture PaymentIntents, idempotency keys) or `fake` (M1 behaviour, used by tests, CI and e2e). With Stripe, a new booking starts in `PENDING_PAYMENT`, the passenger confirms on a Payment Element page, and a verified webhook moves it to `REQUESTED`; the cron reconciles anything a webhook missed. The booking state machine (M1 `transition`) stays the single place statuses change.

**Tech Stack:** M4 stack plus `stripe` (Node SDK), `@stripe/stripe-js`, `@stripe/react-stripe-js` (latest, exact pins). Stripe **test mode only**.

**Spec:** `docs/superpowers/specs/2026-10-28-rideshare-design.md` — §5.3 lifecycle (PENDING_PAYMENT, ABANDONED), §5.6 step 2 (reconcile), §6 Payments (flow + reliability rules), §4 StripeEvent. Baseline: `main` after M4. Carry-overs from `docs/superpowers/m1-followups.md` "M5".

## Global Constraints

- PaymentIntent: `amount` = booking amount in paise, `currency: 'inr'`, `capture_method: 'manual'`, `metadata: { bookingId }`, `automatic_payment_methods: { enabled: true }`.
- Every outbound Stripe call passes idempotency key `${bookingId}:${action}` with action ∈ `authorize | capture | release | refund-<amount>`; this makes `transition()`'s deadlock retry (M1) safe to re-run payment calls.
- Spec §6: the DB state changes only after the Stripe call succeeds; a Stripe failure leaves the booking unchanged and the action returns `PAYMENT_FAILED` "Payment problem — please try again".
- `PAYMENTS_PROVIDER` = `stripe` | `fake`. Default `stripe` when `STRIPE_SECRET_KEY` is set, otherwise `fake`. Tests, CI and e2e use `fake` (bookings go straight to `REQUESTED`, as in M1).
- Webhook: `POST /api/stripe/webhook`, raw body, signature verified with `STRIPE_WEBHOOK_SECRET` (bad/missing → 400, nothing changes). Handled: `payment_intent.amount_capturable_updated` → `AUTHORIZE`; `payment_intent.payment_failed` and `payment_intent.canceled` → `ABANDON` when the booking is still `PENDING_PAYMENT`. Others → 200 ignored.
- Webhook idempotency: if `StripeEvent(eventId)` exists → 200 without processing; otherwise process, then insert the row. A transition that returns `INVALID_STATE` because the booking already moved counts as processed (concurrent duplicate deliveries are serialised by `transition`'s row lock).
- A late `amount_capturable_updated` for a booking that is no longer `PENDING_PAYMENT` (e.g. already ABANDONED) cancels the PaymentIntent so no money stays held.
- Reconcile (cron step 2): `PENDING_PAYMENT` bookings older than 15 min — retrieve the PI; `requires_capture` → `AUTHORIZE`; anything else → cancel the PI (unless already `canceled`) and `ABANDON`. Batches of 100, idempotent.
- `authorize` failure in `requestBooking` abandons the just-created booking (seats returned) and returns `PAYMENT_FAILED` — closes the M1 follow-up "failed authorize leaves the booking holding seats".
- Earnings (demo): per driver, over ACCEPTED and COMPLETED bookings and refunds on CANCELLED ones: `gross = captured − refunded`, `fee = round(gross × 10 %)`, `net = gross − fee`; page labelled "Demo — no money is paid out".
- Env: `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY`, optional `PAYMENTS_PROVIDER`.
- Copy: after paying, "Request sent — your card is held, not charged, until <driver> accepts." Test-mode banner on the pay page: "Test mode: use card 4242 4242 4242 4242, any future date, any CVC."
- All M1–M4 constraints still apply.

## Review Focus

1. **Duplicate or concurrent webhook deliveries** — the same event twice, or two different events racing, cause exactly one transition and no error responses. (Task 3)
2. **Late authorization** — card authorized after the 15-minute reconcile already abandoned the booking: the hold is cancelled, the booking stays ABANDONED, seats are not double-returned. (Task 4)
3. **Stripe down on accept** — capture fails → `PAYMENT_FAILED`, booking stays REQUESTED with its seats, the driver can retry. (Task 1)
4. **Passenger abandons the pay page** — after 15 minutes the reconcile abandons the booking and the seats return to the trip. (Task 4)
5. **Forged webhook** — missing or wrong signature → 400; no StripeEvent row; no booking change. (Task 3)
