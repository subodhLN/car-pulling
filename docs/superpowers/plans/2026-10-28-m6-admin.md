# RideShare M6 (Admin) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give the operator an admin area: platform stats, user moderation (suspend, ID-verify), trip force-cancel, review removal, and a reports queue fed by a "Report" button for users — every action audited.

**Architecture:** An `admin` module holds admin-only services; each one calls `requireAdmin()` (fresh role from the database, never the session claim), does its work through the existing services (`cancelTrip`, `transition`, review recompute) with an `ADMIN` actor, and writes an `AdminAction` row with a required reason in the same flow. A `reports` module lets any signed-in user report a user or trip. Admin pages live under `/admin`, protected in `proxy.ts` and again in the page.

**Tech Stack:** M5 stack. No new dependencies (the bookings-per-day chart is a small hand-written SVG with a table fallback).

**Spec:** `docs/superpowers/specs/2026-10-28-rideshare-design.md` — §8 Admin, §4 (Report, AdminAction), §10.2 (`requireAdmin`, rate limits). Baseline: `main` after M5. Carry-overs from `docs/superpowers/m1-followups.md` "M6" (ruling R21, cancellation attribution, demo admin).

## Global Constraints

- `requireAdmin()` re-reads the user from the database (`role === 'ADMIN'` and `status === 'ACTIVE'`) on every action and page; `session.user.role` is never trusted. Non-admins get `NOT_ALLOWED` from actions and `notFound()` from pages (the admin area's existence isn't confirmed).
- Every admin mutation writes `AdminAction { adminId, targetType ('USER' | 'TRIP' | 'REVIEW' | 'REPORT'), targetId, action, reason }`; `reason` is required, trimmed, 5–500 chars; the audit row is written only if the mutation succeeded.
- Admins act through the normal services with actor `{ kind: 'ADMIN', userId: adminId }`; `actorFor` (user-facing) still never grants ADMIN (R21 stands for the user UI).
- Trips record who cancelled them: new `Trip.cancelledBy CancelledBy?`; `cancelTrip` sets it; passenger-facing copy is "Trip cancelled by the driver" or "Trip cancelled by RideShare" (ADMIN); the cron re-cancel step uses the trip's `cancelledBy` kind (ADMIN → `{ kind: 'ADMIN', userId: null }`).
- Suspend user: status SUSPENDED; their future PUBLISHED trips are cancelled (cascade, full refunds); their own non-terminal bookings as passenger are cancelled by ADMIN (full refund per the refund table); they can no longer log in (M1). Admins cannot suspend themselves or other admins. Unsuspend restores ACTIVE only (cancelled trips stay cancelled).
- Review deletion recomputes the subject's `ratingAvg`/`ratingCount` in the same transaction (M3 `recomputeRating`); deleting the last review shows "New".
- Reports: reasons `UNSAFE | NO_SHOW | INAPPROPRIATE_MESSAGES | FAKE_PROFILE | OTHER`; details ≤ 1000 chars (required for OTHER); one OPEN report per (reporter, target); rate limit 5/hour per user (`report:<userId>`); you can't report yourself; statuses OPEN → RESOLVED | DISMISSED (admin, with note = the audit reason).
- Stats: totals (users, trips, bookings, demo GMV = captured − refunded, paise), bookings created per IST day for the last 30 days, top 10 routes by trip count (origin label → dest label).
- **Demo admin:** with M6, admin powers are real, so the public demo password must not grant them. The seed creates `admin@demo.test` only when `DEMO_ADMIN_ENABLED=true`; the login demo panel lists it only then. Production admins are created with `npm run admin:create -- <email>` (prompts for a password, or reads `ADMIN_PASSWORD`), or by promoting an existing user with `npm run admin:create -- <email> --promote`.
- All M1–M5 constraints still apply.

## Review Focus

1. **Non-admin access** — a USER calling any admin action gets `NOT_ALLOWED`; `/admin/*` pages 404 for users and redirect signed-out visitors to login. (Task 1)
2. **Demoted mid-session** — an admin whose role is changed to USER in the database can't perform the next admin action, even with an old session. (Task 1)
3. **Suspending a busy user** — a driver with accepted passengers and a passenger with an accepted seat elsewhere: all their open bookings end CANCELLED by ADMIN with full refunds, seats return, affected people are notified, and the user can't log in. (Task 3)
4. **Report spam** — a second OPEN report for the same target by the same reporter is refused ("You've already reported this"); the sixth report in an hour is RATE_LIMITED. (Task 5)
5. **Deleting the only review** — the subject shows "New" (count 0, avg 0) afterwards. (Task 4)
