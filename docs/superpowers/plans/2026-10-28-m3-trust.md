# RideShare M3 (Trust) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let drivers and passengers rate each other after a completed ride, show public profiles with ratings, reviews and verification badges, and let users edit their own profile.

**Architecture:** A new `reviews` module owns the Review table and keeps `User.ratingAvg`/`ratingCount` in sync inside the same transaction as each review write. A `users` module serves public profile data (never email or phone) and the self-service profile editor. UI adds a rating form to the existing dashboards, a public profile page, and links to it wherever a person's name appears.

**Tech Stack:** M1/M2 stack (Next.js 16 App Router, TS, Prisma 6 + PostGIS, Auth.js v5, Zod, Vitest, Playwright). No new dependencies.

**Spec:** `docs/superpowers/specs/2026-10-28-rideshare-design.md` — §4 (Review, User rating fields, verification), §5.4 Reviews, §5.5 Profiles, §9 design system. Baseline: `main` after M2. Follow-ups list: `docs/superpowers/m1-followups.md`.

## Global Constraints

- A review is allowed only between the driver and the passenger of a booking whose status is `COMPLETED`; each side may review the other **once per trip** (unique `(tripId, authorId, subjectId)`); no self-reviews.
- Review window: until `trip.departureAt + (trip.durationMin ?? 360) min + 14 days` (spec §5.4 "within 14 days"; the trip has no completedAt column — the cron completes trips at that same arrival instant).
- Rating is an integer 1–5; comment optional, trimmed, ≤ 500 characters, plain text rendered escaped.
- Reviews cannot be edited or deleted by users (admins delete in M6).
- Posting a review updates the subject's `ratingAvg` (Decimal(3,2), rounded half-up to 2 dp) and `ratingCount` **in the same transaction**, computed from the Review table (`AVG`, `COUNT`), never incrementally.
- Ratings display: `ratingCount = 0` → "New"; otherwise `★ 4.8 (12)` (1 decimal). Existing displays in TripRow, trip page and driver dashboard keep this format.
- Public profile shows: name, avatar, "Member since <Month YYYY>" (IST), bio, rating, badges, completed rides as driver and as passenger, latest 10 reviews (author name + avatar, rating, comment, IST date). **Never** email or phone.
- Badges: "Email verified" only when `emailVerified` is set; "ID verified" only when `idVerified` is true. No other claims (spec §9.1).
- Profile edit (own only): name 1–80, bio ≤ 280, phone (same Indian-mobile rule and normalisation as sign-up). Email is not editable.
- Business rules only in services; actions via `defineAction`; pages use `requirePageUser`; `Result`/`ErrorCode` unchanged.
- Rate limit: reviews 10/hour per user (`review:<userId>`) → `RATE_LIMITED` "You've posted a lot of reviews. Try again later."

## Review Focus

1. **Reviewing someone you didn't ride with** — a passenger whose booking was REJECTED/CANCELLED/EXPIRED, or a stranger, posting about the driver must get `NOT_ALLOWED`; only COMPLETED bookings qualify. (Task 1)
2. **Double submit** — two concurrent posts for the same (trip, author, subject) create exactly one review and the rating counts it once. (Task 1)
3. **Rating maths** — 5, 4, 4 → 4.33; a single 1 → 1.00; average stays correct after many reviews (computed, not incremented). (Task 1)
4. **Window edge** — a review at exactly the deadline is accepted; 1 ms after is rejected with `INVALID_STATE` "The review window for this trip has closed". (Task 1)
5. **Privacy on the public profile** — the profile payload contains no `email`, `phone` or `passwordHash`, even for the viewer's own profile. (Task 3)

### Task 1: Review model and service

**Files:**
- Create: `src/modules/reviews/{service,schemas}.ts`, migration `reviews`
- Modify: `prisma/schema.prisma`
- Test: `tests/integration/reviews/service.test.ts`

**Interfaces:**
- Consumes: `db`, `ok/err`, `rateLimit`, factories (`createUser`, `createTrip`), booking rows created directly with `status: 'COMPLETED'`.
- Produces:
  - Prisma `Review { id, tripId, authorId, subjectId, rating Int, comment String?, createdAt }`, `@@unique([tripId, authorId, subjectId])`, `@@index([subjectId, createdAt])`, relations to Trip and User (author/subject named relations). Migration must not drop the hand-maintained objects (check with `npm run db:drift`).
  - `reviewDeadline(trip: { departureAt: Date; durationMin: number | null }): Date`
  - `type ReviewTarget = { tripId: string; subjectId: string; subjectName: string; role: 'DRIVER' | 'PASSENGER' /* subject's role */ }`
  - `pendingReviews(userId: string, now?: Date): Promise<ReviewTarget[]>` — COMPLETED bookings where the user is driver or passenger, deadline not passed, and no review by the user for that (trip, subject) yet.
  - `postReview(authorId: string, input: { tripId: string; subjectId: string; rating: number; comment?: string }, now?: Date): Promise<Result<{ id: string }>>` — validation (`VALIDATION`), relationship check (`NOT_ALLOWED` "You can only review people you travelled with"), deadline (`INVALID_STATE` "The review window for this trip has closed"), duplicate (P2002 → `INVALID_STATE` "You've already reviewed this person for this trip"); in one transaction: insert review, then `recomputeRating(tx, subjectId)`.
  - `recomputeRating(tx: Prisma.TransactionClient, userId: string): Promise<void>` — sets `ratingAvg = ROUND(AVG(rating), 2)` (0 when none) and `ratingCount = COUNT(*)` from the user's reviews; used by `postReview` and by M6 review deletion.
  - `listReviewsFor(subjectId: string, limit?: number /* 10 */): Promise<{ id; rating; comment; createdAt; author: { id; name; image } }[]>`
