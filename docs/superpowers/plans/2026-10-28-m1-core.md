# RideShare M1 (Core) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A deployed carpool web app where users sign up, add a car, publish trips between cities, search by city and date, request seats, and drivers accept/reject — with atomic seat holding, cancellations with the refund policy computed, automatic expiry/completion, and the approved photographic design.

**Architecture:** One Next.js App Router app. Pages call server actions; actions validate (Zod) and authorize, then call module services that hold all business rules; services use Prisma, with raw SQL for PostGIS. Every booking status change goes through one `transition()` function backed by a pure transition table. Payments are a no-op module in M1 whose interface M5 fills with Stripe.

**Tech Stack:** Next.js (latest stable, App Router) · TypeScript (strict) · Tailwind CSS · Prisma + PostgreSQL 16 + PostGIS 3 · Auth.js v5 (`next-auth@5`, `@auth/prisma-adapter`) · bcryptjs · Zod · pino · `date-fns` + `@date-fns/tz` · Vitest · Playwright · Docker Compose · GitHub Actions · Vercel + Neon.

**Spec:** `docs/superpowers/specs/2026-10-28-rideshare-design.md` (read §2–5, §9–12 before starting). Visual reference: `docs/design/home-mockup.html`.

## Global Constraints

- Money is integer paise everywhere (`₹450 → 45000`); format only at render with `formatInr`.
- Timestamps stored UTC; all user-facing dates/“which day” logic use `Asia/Kolkata`.
- Business rules live only in `src/modules/*/service.ts` (or named service files); actions and pages never touch Prisma directly except read-only page queries exported from a module.
- Only `bookings.transition()` changes `Booking.status` after creation.
- Server actions return `Result<T>` = `{ ok: true; data: T } | { ok: false; code: ErrorCode; message: string }`.
- `ErrorCode` = `UNAUTHENTICATED | NOT_ALLOWED | NOT_FOUND | VALIDATION | TRIP_FULL | INVALID_STATE | PAYMENT_FAILED | RATE_LIMITED`.
- Design tokens exactly as spec §9.2; font Figtree 400–800; brand colour only for primary actions, route line, small accents.
- All animation disabled under `prefers-reduced-motion`; follow-cursor only on `(pointer: fine)`.
- UI copy claims only what is true (spec §9.1): no “ID checked” claims unless `idVerified`.
- Vehicle `seats` = passenger seats, 1–7. Trip seats 1..vehicle.seats. Price per seat ₹50–₹5,000 (5000–500000 paise). Departure ≥ 2 h in future. Booking seats 1–4. No requests within 1 h of departure. Request `expiresAt = min(requestedAt + 24h, departureAt)`.
- Refund on cancel: ACCEPTED + passenger cancels > 24 h before departure → full; ≤ 24 h → 0; driver/admin cancels ACCEPTED → full; any non-ACCEPTED booking → 0.
- Search radius default 15 km, allowed 5–50; 20 results per page.
- Rate limits used in M1: sign-up/login 10/min per IP; booking requests 10/hour per user.
- No user-supplied HTML rendered anywhere. Secrets only in env; `.env.example` committed.
- Commit after every task with a conventional-commit message.

## Review Focus

1. **IST day boundaries in search** — a trip departing 00:30 IST on 2 Nov is stored as 1 Nov 19:00 UTC; searching date `2026-11-02` must return it and `2026-11-01` must not. (Task 7)
2. **Double-submitted seat requests** — the same passenger clicking “Request” twice (or two tabs) must yield exactly one active booking and hold seats once. (Task 9)
3. **Accept racing expiry** — a driver accepting a booking the cron has just expired must get `INVALID_STATE`, never an ACCEPTED booking with returned seats. (Task 9)
4. **Exactly-24-hours cancellation** — passenger cancels at exactly `departureAt − 24h` gets no refund (spec says “> 24 h”). (Task 8)
5. **Suspended drivers and cancelled/full trips in search** — they must never appear; a trip with 0 seats left must not appear even for `seats=1`. (Task 7)
